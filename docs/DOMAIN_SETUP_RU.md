# Подключение flareledger.fun

Домен flareledger.fun уже куплен в Vercel. Его можно использовать как с Vercel-проектом, так и с сервером QResto. Сначала выбери, где работает приложение, затем направляй туда DNS.

На предоставленных скриншотах домен ещё не связан с проектом, nameservers имеют статус Pending, сертификаты отсутствуют. Это состояние на момент снимка, а не результат текущей проверки DNS. Также видны выключенное автопродление и запрос заполнить billing address.

Открой [страницу домена](https://vercel.com/denofix-2940/~/domains/flareledger.fun). Проверь актуальные статусы регистрации и nameservers. Обнови недостающий платёжный адрес в настройках аккаунта. Отдельно проверь дату окончания и желаемую настройку автопродления.

## Вариант A Приложение на сервере QResto

Для текущего плана FastAPI, SQLite и Docker это основной кандидат, если Тимофей подтвердит размещение.

1. Получи реальный публичный IPv4 сервера, способ доступа и описание текущего ingress. IP пока не подтверждён.
2. Подними приложение отдельно от QResto и проверь согласованный внутренний upstream. Не меняй владельца портов 80/443.
3. В Vercel DNS создай или измени запись для корня домена: имя @ либо пустое поле, тип A, значение — подтверждённый IPv4 сервера.
4. Проверь имеющиеся записи корня: они не должны одновременно направлять домен в другой upstream. На скриншоте видны автоматически созданные ALIAS. Уточни их управление в текущем интерфейсе Vercel и замени конфликтующее направление при настройке A-записи. CAA не удаляй без необходимости.
5. Если нужен www, настрой его отдельно и добавь соответствующий hostname или redirect в ingress. AAAA добавляй только после проверки работающего IPv6 на сервере.
6. Тимофей добавляет flareledger.fun в уже работающий Nginx, Caddy, Traefik или иной ingress. Этот ingress получает и продлевает сертификат для внешнего сервера.
7. Проверь DNS и HTTPS с другого устройства и внешней сети.

Для этой схемы подключать домен к Vercel-проекту не требуется. TLS внешнего сервера настраивается на самом сервере, а не кнопкой загрузки сертификата в Vercel. Действующие DNS-записи выбираются по реальному адресу, не по подсказке 76.76.21.21 в поле ввода.

## Вариант B Frontend в Vercel

1. Сначала нужен настоящий frontend с package.json, package-lock.json и рабочей сборкой. Текущая структура папок ещё не является приложением для деплоя.
2. Открой [New Project](https://vercel.com/new) и импортируй Denofix/flareledger.
3. После реализации выбери Root Directory frontend, framework Vite, install npm ci, build npm run build и Output Directory dist. Сверь эти команды с реальным frontend.
4. Сначала проверь выданный адрес vercel.app.
5. В настройках проекта открой Domains и добавь flareledger.fun. Используй предложенные именно этому проекту DNS-настройки и дождись подтверждения конфигурации.
6. После проверки домена Vercel автоматически выпускает управляемый TLS-сертификат. Покупать отдельный SSL-сертификат для этого варианта не нужно.
7. Для работающего /api отдельно требуется размещённый backend и правильно настроенный маршрут к нему. Корпус, база и LLM-ключи не размещаются в публичном каталоге frontend.

Покупка домена не развёртывает FastAPI и не создаёт постоянный SQLite volume. Полный backend в Vercel потребует отдельного согласованного изменения архитектуры. Для старта можно выбрать frontend на Vercel и backend на подтверждённом сервере, сохранив /api через proxy rewrite после появления реального HTTPS upstream.

## Проверка из Ubuntu

```bash
sudo apt install -y dnsutils curl
dig +short NS flareledger.fun
dig @1.1.1.1 +short A flareledger.fun
dig @1.1.1.1 +short AAAA flareledger.fun
dig +short CAA flareledger.fun
curl -I https://flareledger.fun
```

После настройки A-запись должна соответствовать выбранному серверу или конфигурации Vercel. HTTPS должен открываться без ошибки сертификата. Для готового приложения отдельно проверяются главная страница, SPA-маршруты и /api/health/ready; отсутствие этих маршрутов на стадии структуры репозитория ожидаемо.

## Что запросить у Тимофея

- Подходит ли QResto по ресурсам, доступу и разрешению владельца.
- Публичный IP и наличие рабочего IPv6, если он вообще нужен.
- Какой ingress уже обслуживает 80/443 и кто добавляет hostname.
- Какой upstream выделяется FlareLedger и как он изолирован от QResto.
- Где сохраняются SQLite, corpus и резервная копия, кто проверяет восстановление.
- Кто проверяет HTTPS извне и до какой даты сервер будет доступен.

После ответа достаточно зафиксировать один основной способ размещения. Дополнительный домен покупать не требуется.
